# Устройство системы

## Отчёты и данные

Сайт Flask обслуживает HTML и выгрузки. Общий исполнитель (`worker --task all`) последовательно выполняет задания; отдельный монитор (`worker --task monitor`) продолжает читать правки и категории во время обработки. HTTP-запрос не запускает долгий скрипт: он добавляет задание в базу, поэтому закрытие вкладки не прерывает обработку. Проверка очереди выполняется каждые 5 секунд, чтение событий Википедии — по настроенному интервалу поиска. Свободный обработчик подхватывает ручной запуск в течение 5 секунд; при занятом обработчике запуск ждёт текущую работу.

На Toolforge используется общая MariaDB ToolsDB. Локально — SQLite в `var/`. Локальный SQLite не следует переносить на общий NFS Toolforge: для нескольких процессов предназначен вариант с ToolsDB.

Таблицы:

| Таблица | Содержимое |
| --- | --- |
| `pages` | Последняя проверенная версия, текст, результаты анализа, время проверки |
| `jobs` | Ожидающие задания, срок, режим форматирования, версия и повторные попытки |
| `runs` | Полная история, события, различия, снимок отчёта, итоговая таблица |
| `state` | Позиция чтения RecentChanges, состояние наблюдения, временные OAuth-запросы |
| `leases` | Общая блокировка обработки, блокировка диспетчера и отдельные блокировки действий/наблюдения |

В режиме проверки отчёт соответствует **фактическому тексту страницы**. Предлагаемое исправление доступно в журнале как различие. После успешной записи анализируется сохранённый текст. Частичная обработка обновляет только затронутые страницы; оставшаяся часть отчёта сохраняется. У каждой записи есть время проверки и версия.

`no_itog` и `sub_itog_no_main` объединяются в список открытых номинаций, записи с подитогами отмечены отдельно. Остальные проверки относятся к проблемам оформления.

## Общие таймеры

`schedules.py` определяет три типа: ежедневный запуск (`daily`), пауза после правки (`after_edit`) и форматирование последнего дня месяца (`month_end`). Задача перечисляет поддерживаемые типы в `Task.schedules`; определение поля, проверка, сохранение, расчёт срока и HTML-редактор используют общие методы. Новым обработчикам доступны те же типы без отдельной формы или маршрута.

admin сохраняет расписание через POST `/admin/tasks/<slug>/schedule` с CSRF. Настройки хранятся в `state` по ключу `<slug>:config`; независимые формы обновляют только свои поля. Значения из окружения остаются начальными значениями ОБКАТ, ежедневный запуск по умолчанию — 03:00 МСК. Пауза ограничена 1–1440 минутами, время — ЧЧ:ММ. Некорректная форма целиком отклоняется.

Исполнитель и монитор читают расписание из базы без перезапуска. Изменение паузы оставляет запрос на пересчёт: наблюдатель получает последние версии ожидающих страниц и переносит сроки от фактического времени правки. Новые события не теряются; начатые задания и задержки повторных попыток после ошибок не переносятся. Перед обработкой страницы также проверяется текущая пауза. При ошибке API запрос на пересчёт сохраняется.

Изменение ежедневного времени отменяет только будущие задания расписания; просроченные и ручные сохраняются. Время месячного форматирования переносит ожидающее задание текущего месяца, не затрагивая догоняющие задания предыдущих месяцев. Уже выполненный месячный проход не повторяется при переносе времени на более позднее.

## Правки → очередь → обработка

1. Обработчик раз в 5 минут читает `RecentChanges` пространства «Википедия», включая новые страницы. Отбирает только названия вида `Википедия:Обсуждение категорий/<Месяц> <Год>` начиная с настроенного месяца.
2. Для новой версии сохраняет одно задание страницы со сроком `время правки + 15 минут`. Новая версия обновляет срок того же задания. Перекрытие двух секунд на границе запросов не создаёт повторов.
3. При наступлении срока заново скачивает последнюю версию. Если появилась свежая правка, откладывает задание.
4. Форматирует и анализирует страницу. При включённой записи использует `baserevid` и `basetimestamp` в API: конфликт версий приводит к повторной попытке, а не перезаписи правки участника.
5. Пересобирает таблицу открытых номинаций из всей проверенной копии страниц. Публикация разрешена только после получения полной копии всех месяцев; локальный импорт не считается проверенной копией Википедии.
6. Сохраняет журнал и снимок отчёта. Успешное задание удаляет из очереди; сбой оставляет в ней со сроком повторной попытки от 2 минут до 1 часа.

Проверка изменений выполняется часто, но сама обработка запускается по событиям. Раз в сутки проводится сверка **номеров версий**, чтобы восстановить пропущенные события, удаления и события после долгого простоя. Она не форматирует неизменившиеся страницы. После пропущенного события запускается только изменившаяся страница. Первая синхронизация — отдельное задание всех месяцев.

Собственная успешная запись бота обновляет сохранённый номер версии; событие об этой же версии не создаёт новый запуск. Более новая версия, даже от того же пользователя, снова ставится в очередь.

Исполнитель выбирает готовые активные задания в порядке списка: ОБКАТ → даты → параметры RQ → разворачивание RQ → переводы через категории → переводы с СО. Будущие сроки и паузы не препятствуют следующим действиям. Начатый проход не вытесняется новой задачей. Внутри ОБКАТ ручной запуск имеет приоритет перед отдельными страницами; первичная синхронизация — перед обычными заданиями. При большой очереди обработка может начаться позднее 15 минут. Общий `processors/daily_worker.py` обслуживает расписание, команды и исполнение всех ежедневных действий; `processors/daily.py` связывает их настройки и отчёты с одним HTML-интерфейсом.

Диспетчер ставит ежедневные действия в очередь перед выбором первого; за один цикл каждое действие может выполнить один проход. Общая блокировка `execution` в базе исключает параллельную обработку даже при запуске старых команд отдельных задач. Она продлевается перед запросами API и истекает через 10 минут после аварийной остановки. Потеря блокировки останавливает старый процесс перед следующей операцией. Независимые блокировки наблюдения позволяют монитору продолжать чтение без занятия места обработки.

## Конец месяца

По умолчанию в последний день календарного месяца после 23:30 в `Europe/Moscow` создаётся одно задание `month_end:YYYY-MM`. Оно эквивалентно старому `ENABLE_SPACING_FORMAT=True`, включая нормализацию пустых строк.

Свежие страницы откладываются в отдельные задания с сохранённым флагом форматирования. Ежемесячный проход может поэтому завершиться в следующем месяце. Успешный проход отмечается в базе и не создаётся повторно. Если уже работающий сервис пропустил конец месяца из-за простоя, после восстановления запускается один актуальный пропущенный проход; все исторические месяцы по отдельности не догоняются. При самом первом развёртывании исторические ежемесячные проходы не запускаются.

Ручной запуск начинает обработку сразу после получения задания и не ждёт паузы в 15 минут; защита от конфликта версий действует. Кнопка «С форматированием» не меняет глобальный режим: форматирование включается только для этого запуска.

## Задачи и управление

На главной восемь действий из общего реестра `TASKS`, сгруппированных в четыре раздела. Подключены ОБКАТ, три действия шаблонов, два действия переводов и два направления замены шаблонов разделов. Настройки, источники, журналы и управление независимы для каждого действия. Общая страница обновляет состояние каждые 15 секунд; во время чтения раскрытого пояснения обновление ждёт закрытия панели.

Действия разделов используют тот же `DailyWorker` и `article_checks`, что переводы. Источники — включения целевого шаблона и его перенаправлений в пространство 0 через `embeddedin`. Монитор сверяет их каждые 6 часов, исполнитель по умолчанию допускает оба направления в очередь в 04:00 МСК. Кеш перенаправлений и его просмотр доступны в параметрах; полные рабочие настройки, ручное обновление и «С нуля» доступны admin. Подробные правила: [SECTIONS.md](SECTIONS.md). В общей очереди эти направления идут после переводов.

Действия переводов выбирают только новые статьи относительно постоянного учёта `article_checks`, отдельно для категорий и СО. Отсутствие источника и другие законченные проверки исключают название из будущих обычных проходов, сохраняя причину в отдельном списке пропущенных. Пропуски не увеличивают число ручных исправлений; конфликты относятся к ручным проблемам, технические сбои отражаются в состоянии запуска. Технические сбои и несохранённые предложения не создают отметку. Задание `recheck` сбрасывает отметки только своего действия при начале исполнения; идентификатор задания в состоянии не даёт повторить сброс после паузы. Журналы запусков сохраняются.

Публичный интерфейс показывает названия, состояния, даты и число ручных исправлений; у шаблонов и переводов также число статей к обработке. Пояснения спрятаны под «?», управление и настройки видны под admin. Публичные журналы ОБКАТ содержат все действия и различия. Для дат, RQ и переводов HTML/TXT/JSON показывают только статьи с сохранёнными изменениями и изменённые шаблоны: даты либо язык и оригинал. Полные журналы с историей, настройками и различиями доступны только admin. Публичные остатки размещены отдельно в отчёте. Подробнее: [обработка шаблонов](MAINTENANCE.md), [источники переводов](TRANSLATIONS.md).

Все страницы задач следуют схеме «обзор и управление → сворачиваемые параметры → результаты и отчёты». Очередь ОБКАТ публично показана сверху рядом с правилами таймеров; расширенные сведения об очереди доступны администратору. В отчёте по номинациям вкладки «Проблемы» с инструкциями, «Открытые номинации» с непрерывным списком и последняя вкладка «Лог» с историей запусков. Открытая номинация и её подитоги объединяются по странице и строке заголовка; исходные записи анализа и выгрузки сохраняются. У истории собственная пагинация; подробный журнал каждого запуска открывается отдельной страницей. Будущие обработчики получат те же таймеры и компоновку при переносе.

Состояние исполнения и состояние фонового процесса отображаются отдельно. Задача может быть выполнена и ожидать следующего события, находиться в очереди, выполняться, завершиться ошибкой, стоять на паузе или быть остановлена. Текущее исполняемое задание не считается следующим; более новая правка той же страницы остаётся в очереди. Импорт файлов показан как снимок, а не запуск бота.

Команды admin хранятся в `state` по идентификатору задачи:

- **Пауза** прекращает проход перед следующим запросом/страницей и сохраняет очередь. Наблюдение за правками продолжает собирать задания.
- **Продолжить** разрешает обработку сохранённой очереди.
- **Остановить** отменяет очередь и отключает наблюдение и новые автозапуски этой задачи.
- **Перезапустить** прерывает старый проход, заменяет очередь одним полным запуском и включает задачу. Сверка версий выполняется заново.

Уже отправленный запрос API нельзя отозвать: он завершается, а его результат сохраняется в журнале и отчёте. Проверка поколения команды перед следующей операцией предотвращает продолжение старого прохода даже при быстрой паузе и возобновлении. Команды сохраняются в базе, поэтому перезапуск процесса не снимает паузу или остановку. Остановки и паузы записываются как отдельные статусы запусков в публичной истории.

## Доступ

Отчёты и история доступны без входа; различия и полная диагностика дат/RQ/переводов доступны admin. Единая публичная проекция применяется ко всем форматам журналов этих задач; выгрузки ОБКАТ не принимают идентификаторы их запусков. Wikimedia OAuth подтверждает имя пользователя. Сессия хранит только подтверждённое имя и служебные идентификаторы; секреты незавершённого OAuth-запроса хранятся в базе. Полученный пользовательский access token не сохраняется и не используется для правок.

Кнопки управления доступны роли admin: она назначается учётной записи Wikimedia из приватного параметра `TOOLFORGE_ADMIN_USERNAME`. Пустое значение отключает управление. Все изменения состояния через сайт — POST с CSRF-токеном. Правки делает отдельно настроенная учётная запись бота через BotPassword. Пароли, токены, куки и параметры авторизации не включаются в публичные журналы.

Статус страницы обновляется каждые 3 секунды без замены редактируемой формы настроек. `/console` и `/console/fragment` доступны всем; admin получает полную диагностику, остальные пользователи — публичные события: события всех действий, фильтр по действию, очередь и ссылка на полный журнал. Консоль показывает последние 200 событий из 15 последних проходов; полная история сохраняется в отдельных журналах. Отключение слежения приостанавливает обновление консоли для чтения.

Служебные ошибки процесса доступны в выводе задания Toolforge и журнале по правилам доступа своего модуля. Отмена внешнего задания или перезапуск отмечают незавершённый журнал как прерванный. ОБКАТ продолжает сохранённое задание; ежедневные действия после аварии ждут следующего ежедневного запуска.

Обработчик учитывает запреты `{{nobots}}` и `{{bots|allow=…|deny=…}}`. Такие страницы анализируются, но их изменения пропускаются и явно отмечаются в журнале. Между попытками записи выдерживается минимум 10 секунд (`TOOLFORGE_EDIT_INTERVAL`).


## Наблюдения и сбои

`schedules.py` задаёт также общий таймер поиска `search_minutes`: 5 минут для ОБКАТ, 360 для ежедневных действий. Изменение читается следующей итерацией монитора. Последний успешный поиск показывается отдельно от последней обработки.

`problem_history` хранит устойчивый ключ проблемы, область наблюдения, первое/последнее подтверждение, устранение и число появлений. Номера строк не входят в ключ. `issues.py` принимает время фактической проверки; повторный показ кеша не обновляет даты, старые снимки не отменяют более новые наблюдения.

`notifications` хранит историю инцидентов с уникальным активным ключом, прочтением и автоматическим устранением. `health.py` собирает состояния процессов, устаревшие данные, пропущенные сроки и ошибки запусков. `GET /notifications` доступен admin; изменения прочтения требуют POST и CSRF.

Выборочная повторная проверка — задание `article` с названием и хешем в ключе. Она занимает тот же слот `execution`, обходит отметку только выбранной статьи, заново подтверждает принадлежность источнику и сохраняет остальные отметки. При техническом сбое задание переносится на следующий ночной срок, включая восстановление после падения процесса.
